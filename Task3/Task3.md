## Проблема

Видимо ошибки возникают, т.к. при запросе к разным API может возникнуть необрабатываемая ошибка и это может положить весь запрос получения продуктов. Тогда при подключении новых партнеров запрос будет только расширяться и вероятность ошибки только повышаться.

## Варианты

### 1. Сделать небольшое хранилище для сервиса интеграции
- сервис с какой-то периодичностью опрашивает внешние API раздельными запросами;
- сохраняет полученную информацию в виде, удобном для внутренних процессов системы;
- в зависимости от того, возвращают ли внешние API полный перечень актуальных продуктов или только новые продукты, перезатирает или добавляет данные о страховых продуктах у себя в хранилище;
- в случае ошибок того или иного сервиса - данные не обновляются;
- может хранить дату последнего обновления данных по продуктам каждой компании, чтобы предупредить, что их давно не получалось обновить.

При запросе к этому сервису изнутри приложения он будет возвращать данные из своего хранилища.

Ключевые плюсы - не нужно менять логику запросов от других сервисов к сервису интеграции. Риски неожиданной структуры данных от партнеров будут обрабатываться внутри сервиса и не затронут core.

Ключевые риски - нужно создать хранилище и реализовать запись данных туда, переделать поведение при запросе от других сервисов.

### 2. Сделать появление новой информации о продуктах как публикацию событий.
- сервис с какой-то периодичностью опрашивает внешние API раздельными запросами;
- в случае успеха публикует полученные данные в топик Kafka;
- ошибки интеграции могут писаться в Kafka, чтобы дать понять потребителям, что сервис не доступен и информация о продуктах может быть устаревшей;
- сервисы приложения подписываются на топик и сами забирают себе новую информацию о продуктах в локальные хранилища.

Ключевые плюсы - при появлении новых потребителей информации о продуктах - логику обработки первички можно будет реализовать в них, без доработок сервиса интеграции. Не нужно дополнительное хранилище.

Ключевые риски - неожидаемая структура данных о продуктах должна обрабатываться на стороне сервисов-потребителей. В принципе значительно больше доработок на стороне сервисов-потребителей.


## Итог
Более предпочтительным кажется первый вариант, потому что он полностью возлагает ответственность на данные о продуктах на один сервис и делает его надежным поставщиком данных. Все аспекты взаимодействия и качества данных от внешних систем не затрагивают другие сервисы системы.

На схеме добавлена БД сервиса ins-product-aggregator.

## Возможные сопутствующие доработки
В системе также присутствует процесс передачи данных о взаиморасчетах во внешние API. В этом процессе хорошо было бы добавить transactionOutbox для сервиса ins-comp-settlement. Роль отправщика сообщений может взять на себя компонент внутри ins-comp-settlement, либо эту фукнцию возложить на ins-product-aggregator, чтобы вся логика взаимодействия с внешними системами была внутри одного сервиса.

На схеме добавлен TransactionOutbox в потоке между ins-comp-settlement и внешними системами.
